## C. IA caída → pantallas usables

No apagar AI8000, cambiar el gateway, retirar consentimiento para fingir una
caída ni reiniciar el stack. Preparar dos evidencias con etiquetas distintas:

- **UI con fallo HTTP controlado**, en el navegador de QA de front: interceptar
  únicamente los endpoints ERP de ai-summary y ai-suggestions del aiPatient.
  Devolver el contrato de degradación **200**
  `{status:'unavailable',summary:null}` / `{status:'unavailable',draft:null}`;
  en un subcaso, error de red del mismo endpoint para comprobar catch/reintento.
  No interceptar datos APP, tests, plan semanal, nutrición, recursos o login.
  El bloque IA se omite/muestra el feedback seguro previsto por 4.7/4.8; el Perfil
  360 y editor manual siguen presentes. En APP, Protocolo/Nutrición/Perfil/Tests
  siguen navegables con sus datos reales y sin cambios por IA. No guardar ni
  aplicar desde el editor para demostrar solo que sigue habilitado.
- **Fallo real del proveedor atravesando backend**, separado: reutilizar las
  simulaciones y pruebas de cliente BACK `patient-summary.sim.yaml` y
  `weekly-suggestions.sim.yaml` contra instancia aislada autorizada, con el
  código backend real como consumidor y 503/timeout en el proveedor. La skill
  `postman:api-simulation` describe ese montaje. No redirigir el stack compartido.
  Registrar requests capturados y resultado backend unavailable. El subcaso UI
  anterior por sí solo **no acredita** que un LLM caído degrade de extremo a extremo.

Después de retirar las rutas controladas, repetir una lectura sana y comprobar
que no quedan interceptores. Un 401, 403 o consentimiento ausente no prueban
caída de IA. No transformar unavailable en una sugerencia falsa o reutilizar
un draft viejo como recién generado. El borrador previo y el plan permanecen.
