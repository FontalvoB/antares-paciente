# 3.20 — preparación APP para codex-front

La integración 3.18/3.19 aceptada es `5f86c52`; este prep añade únicamente
selectores de presentación y el harness HTTP reproducible. **No contiene el spec
3.20**. El ejecutor de ese e2e será codex-front cuando 3.17 esté disponible.

## Selectores estables, independientes del idioma

Usar `getByTestId`. Los atributos no contienen IDs internos ni amplían D0014.

| `data-testid` | Uso / alcance |
| --- | --- |
| `nutrition-tab-plan` | Segmento Plan, tras entrar en Nutrición. |
| `nutrition-plan` | Plan disponible, `data-state="summary"` o `"detail"`. |
| `nutrition-plan-details` / `nutrition-plan-summary` | Abrir detalle completo / volver al resumen. |
| `nutrition-recommendations` | Tarjeta actual o tarjeta dentro de un ciclo anterior; `data-state="loading\|empty\|error\|ready"`. |
| `nutrition-recommendation-message` | Texto publicado; es texto plano. |
| `nutrition-recommendation-professional` / `nutrition-recommendation-publication` | Profesional y fecha visible. |
| `nutrition-history-open` / `nutrition-history-back` | Abrir ciclos anteriores / regresar a Plan. |
| `nutrition-history` | Región del historial; mismos cuatro estados. |
| `nutrition-history-cycle` | Cada fila, en el orden recibido de `previous`. |
| `nutrition-history-cycle-toggle` / `nutrition-history-cycle-hide` | Abrir/cerrar el acordeón; se buscan dentro de su fila. |
| `nutrition-recommendation-attachment` | Cada figura; buscar imagen, pie y acciones dentro de ella. |
| `nutrition-recommendation-image` / `nutrition-recommendation-caption` | Host `ion-img` con `src` firmado intacto / pie si no está vacío. |
| `nutrition-recommendation-image-error` / `nutrition-recommendation-image-refresh` | Estado caducado / Actualizar mediante otro GET. |
| `nutrition-recommendations-retry` / `nutrition-history-retry` | Reintento de fuente; deshabilitado si no procede (401/403 o fetch activo). |

En estado ready, tarjeta y fila del ciclo llevan `data-cycle-number` y
`data-published-at`, tomados del DTO público. El número identifica el **ciclo
revisado**; no equivale al ciclo vigente del plan. La fecha se conserva ISO en el
atributo y se presenta `dd/mm/aaaa` en pantalla. No deducir programa ni ordenar
filas por número. No asumir que un número de ciclo es un identificador único:
comparar cada fila con `previous[index]` y su publicación.

La tarjeta se reutiliza en el historial: evitar un `getByTestId` global que asuma
unicidad. Buscar dentro de `nutrition-history-cycle.nth(index)`. En Plan el
historial no está montado y la tarjeta actual es única. En Ionic, el `data-testid`
está en el host; Playwright hace click en él. Para confirmar imagen decodificada,
esperar `complete && naturalWidth > 0` en el `img` de su shadow root. No depender
de clases CSS para localizar el control ni de sleeps para las respuestas.

## Recorrido que ejecutará codex-front

1. Levantar ERP, APP y gateway/back F3 compatibles con 3.17/3.10. Usar dos
   sesiones distintas: profesional en ERP y paciente con JWT `aud=app` en APP.
   Nunca reutilizar el token ERP para el autoservicio. Entrar en Nutrición con la
   navegación normal de la app, que sigue siendo por estado, sin ruta `/nutrition`.
2. Preparar/publicar mediante la UI 3.17 una recomendación de un ciclo revisado
   del paciente QA, con mensaje ES/EN aprobado y al menos una imagen visible con
   pie. Conservar una publicación anterior y, para el caso vacío, un paciente sin
   publicaciones. No crear endpoints de fixture ni enviar IDs a 3.10 desde APP.
3. Antes de entrar en Nutrición o cambiar idioma, preparar una espera de respuesta
   para **GET `/api/v1/me/nutrition/cycles/recommendations`** sin query/body. La
   consulta puede empezar antes de pulsar Plan: se monta con NutritionPage.
   En ES/EN verificar `X-App-Language` y `Accept-Language`, y la forma
   `{ current, previous }`. El servidor decide identidad, selección y orden.
4. Pulsar `nutrition-tab-plan`. Esperar `nutrition-plan` y tarjeta ready. Comparar
   texto, profesional, ciclo revisado y publicación con `current`; no con el ciclo
   del plan ni con el mayor número. Comprobar adjuntos y pies visibles, sin notas
   internas, borrador ni IDs. Abrir detalle de Plan y volver al resumen.
5. Abrir `nutrition-history-open`. Esperar región ready y comparar filas por
   posición con `previous`. Abrir/ocultar una fila mediante sus selectores, comprobar
   recomendación/adjuntos y regresar con `nutrition-history-back` sin perder Plan.
6. Con 200 `{ current:null, previous:[] }`, comprobar tarjeta empty, Plan usable y
   ausencia de contenido inventado. Si el historial abierto recibe `previous:[]`,
   comprobar su empty y que el retorno siga disponible. No convertir 404 sin
   perfil ni un fallo de red en este vacío.
7. Comprobar carga independiente y fuente 503 con Plan usable y retry que vuelve
   a pedir el envoltorio. Los fallos controlados se pueden interceptar en el
   límite HTTP; mantener separado ese resultado del escenario de publicación real.
8. URL caducada: capturar el `src` inicial. Para ejercer rápidamente la rama de UI,
   devolver 403 **solo para esa URL de imagen**, sin sustituir el GET real de 3.10.
   Esperar image-error y pie conservado. Registrar la espera del siguiente GET
   **antes** de pulsar image-refresh. Comprobar nueva respuesta/URL y decodificación
   de imagen, sin cache-buster añadido por el cliente. Esto prueba recuperación del
   cliente; la caducidad criptográfica real de Storage requiere una comprobación
   separada con firma vencida. No esperar cinco minutos con el polling activo:
   la app renueva preventivamente a los cuatro.
9. 401: comprobar el refresh compartido y, si también responde 401, invalidación
   de sesión sin bucle ni datos previos. En la APP completa el puente de auth
   devuelve al login; no exigir que el mensaje local siga montado tras navegar.
   El harness aísla AppContext y deja visible el mensaje de sesión caducada. Con
   403 se muestra falta de acceso y retry deshabilitado, sin refresh de credenciales.
10. Repetir Plan/historial/estados a 320/390/768 y ES/EN. Guardar capturas después
    del fin de animaciones y carga de imágenes visibles. Registrar consola y red:
    cero errores en recorrido sano; HTTP 401/403/503 inyectados identificados aparte,
    cero pageerrors/errores JS o peticiones inesperadas y sin overflow horizontal.

En el e2e real, la respuesta de 3.10 y las URLs deben venir del backend. El harness
que sigue no acredita persistencia, privacidad entre pacientes, selección en BD,
traducciones aprobadas ni firmas reales. Esas garantías corresponden a **3.20**.

## Harness local versionado para Playwright MCP

Ficheros: `scripts/qa/nutrition-recommendations/setup-playwright.js`,
`smoke-playwright.js` y `vite.config.mts`. Son funciones para
`browser_run_code_unsafe`, sin imports desde el producto. El setup sirve HTML de
prueba por interceptación, monta la NutritionPage conectada y usa hook, servicio,
apiFetch y auth reales. Solo las respuestas HTTP de 3.10 y las imágenes son stub;
las demás fuentes de la pantalla se aíslan para no depender del stack compartido.

Desde el worktree, iniciar **en background**, con ventana oculta y logs separados:
`node node_modules/vite/bin/vite.js --config scripts/qa/nutrition-recommendations/vite.config.mts --host 127.0.0.1 --port 5182 --strictPort`.
Usar `Start-Process`, comprobar antes puerto libre y después HTTP 200. La config
reutiliza la del producto y desactiva HMR solo para esta revisión. No matar procesos
ajenos. Crear previamente el directorio de evidencia.

En una llamada de Playwright MCP, configurar en el objeto `page` (no en `window`):
`page.qaConfig = { origin:'http://127.0.0.1:5182', output:'<directorio absoluto de evidencia>' }`.
Ejecutar el setup por `filename` con su ruta desde la raíz habilitada del workspace.
Después configurar `page.qaCase = { width:320, lang:'es' }` y ejecutar el smoke por
`filename`; repetir para 390/768 y en. El setup lee la fixture del DTO congelado de
tests y genera URLs de prueba renovadas en cada GET, conservando sus cinco minutos.
No lleva rutas absolutas del equipo ni necesita credenciales reales.

El smoke comprueba doce recorridos por combinación, incluido current null,
caducidad 403 con refetch y 401 definitivo con un único refresh. Guarda 11 capturas
por combinación y acumula `page.qaResults` con método/ruta/idioma/estado/presencia
booleana de Bearer, sin tokens. Los 401/403/503 inyectados aparecen en consola/red;
conservarlos como fallos esperados, no silenciarlos. Al terminar guardar resultados,
abrir un recorrido sano nuevo para su consola limpia y cerrar pestaña/servidor propio.
